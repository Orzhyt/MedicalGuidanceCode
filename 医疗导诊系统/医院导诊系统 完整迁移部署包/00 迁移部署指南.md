# 医院导诊系统迁移部署

本包用于已有自托管 Dify 的目标环境，核验基线为 Dify 1.9.1。医院服务、两份工作流、知识库、接口协议及学员材料都随包提供。部署需要 Docker Compose、可获取的 langgenius/dify-api:1.9.1 镜像和一个可用的 LLM。Dify 平台本体由目标环境提供。

## 1 启动医院服务

解压到目标主机。医院服务和 Dify 必须共享一个可访问网络。默认 docker_default；执行 docker network ls 确认目标名称。名称不同，复制 .env.example 为 .env 后修改 DIFY_DOCKER_NETWORK。MEDICAL_HOST_PORT 可改宿主机监听端口；容器内仍为 8095。若已有同名医院服务，请使用独立网络或调整命名，避免两个同名服务相互干扰。

在解压目录执行：

    docker compose config --quiet
    docker compose up -d --wait
    docker compose ps
    curl http://127.0.0.1:8095/health

健康检查返回 ok=true。deployment/SERVICE_API_KEY.txt 和 deployment/service-key.env 包含同一明文服务密钥，Compose 已读取后一份。新数据卷首次启动按该值初始化 API 密钥，患者令牌签名密钥自动生成。已有数据卷继续使用该卷自己的密钥，不覆盖历史数据。Dify 工作流使用的容器地址为 http://medical-guidance:8095；127.0.0.1 是宿主机地址，不能直接用在容器内的 HTTP 节点。

如果 Dify 通过 SSRF 代理访问内部接口，确保代理也加入可解析 medical-guidance 的网络。按 deployment/ssrf_proxy_medical.conf 为该服务名和 8095 端口加入定向例外，放在安全端口限制和管理接口规则之后、末尾 deny all 之前。按目标环境的方式重载代理；不要用这段覆盖整个 Squid 配置，也不要关闭全局保护。根目录的同名文件是原本机环境的历史路由片段。

## 2 导入知识库和两份工作流

1. 在 Dify 的“知识库”上传 knowledge/导诊知识库.md，创建“医院导诊知识库”。选择通用分段与经济索引，按手册配置分段和 Top K。文档变成“可用”后，用“耳鸣”召回测试，检查 K09。knowledge/sources.json 为资料来源清单。
2. 在“工作室”分别用“导入 DSL 文件”导入 exports/consultation.yml（Chatflow）和 exports/booking.yml（Workflow）。使用 exports/ 下的文件；根目录的同名 YAML 是构建材料。
3. 打开咨询流程的“查找相关导诊资料”，重新选择新建的知识库，确认查询变量和 Top K=6。原部署知识库 ID 无法跨工作区复用。
4. 打开咨询的两个 LLM 节点，选目标工作区可用的模型。原配置是 DeepSeek V4.1 Flash（deepseek-flash），需要模型供应商凭据；如替换模型，重新验证 JSON 输出和对话行为。
5. 核对两个应用的 API_BASE_URL 和 SERVICE_API_KEY。部署包 DSL 已预填本包提供的医院服务地址与明文密钥；如果 Dify 导入后清空了 Secret 字段，从 deployment/SERVICE_API_KEY.txt 粘贴。若沿用旧数据卷，以该卷实际使用的服务密钥为准。
6. 界面试跑通过后，再发布两个应用。在各自“访问 API”创建新的应用密钥，分别配置给可信业务后端。client.env.example 列了 client_example.py 所需变量；不把三种密钥放进患者浏览器。

## 3 验证与对接

- 医院接口自检：python deployment/smoke_service.py 。只读查询，无预约写入。端口改动时传入完整服务地址作为第一个参数。
- 在预约 Workflow 的运行面板，booking_payload 填 {"action":"query","doctor_id":"2"}，patient_token 留空。检查返回的 code、message 和 result_json。输入 {"action":"not_supported"} 应返回 INVALID_INPUT。
- 咨询 Chatflow 新开会话输入“耳鸣”，再答“三天了，听力正常，想挂明天的号”。检查先有简短问询，再给专科方向和实际余号；选择候选只产生预约交接信息，不能显示已占号。
- 真实联调步骤见 API对接说明.md 和开发文档第9章。业务后端读取本轮私有记录、核对身份和提交事件、签发实验患者令牌、调用预约 Workflow。HELD 为占位，CONFIRMED 才是预约成功。前台及业务后端的成品界面未包含；client_example.py 是接口示例。
- tests、reports 和 test_*.py 提供单元测试、接口回归、并发及历史验证材料。test_*.py 多为原环境容器内脚本，含原测试路径，跨机执行先按目标环境改地址和测试配置。启动和界面验收优先按本说明。
- 新服务初始化测试医生和滚动号源；本包没有源数据库、历史预约、私人咨询数据、源 Dify API 密钥、模型密钥或源签名密钥。

## 4 文件定位

- exports：两份已发布工作流的迁移 DSL。
- knowledge：知识库原文和来源。
- service.py、compose.yaml、deployment：医院接口服务、Docker 部署、明文服务密钥、代理配置和健康自检。
- 开发文档、API对接说明、openapi.json、client_example.py：业务、接口及前后台对接。
- nodes、提示词、构建脚本、测试、报告、流程图：实现和验收资料。
- 学员手册与配套材料：两份已确认 Word 指南及复制材料。授课时把这里的材料与管理员用的 exports 分开。
- skills：中文 Dify 操作指导及业务工作流经验。
- CHECKSUMS-SHA256.txt：ZIP 内所有交付文件的 SHA-256（清单本身除外）。
