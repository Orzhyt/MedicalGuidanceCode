# 医院导诊系统 2.2

包含咨询追问推荐 Chatflow 和医生档期预约 Workflow，已在本机发布。

患者回复简短，不展示参考资料或JSON。病情追问最多三轮，预约意向继续多轮确认；科室把握低时转全科初诊。简短主诉先做必要的护士基础问询，已知信息不重问；完成必要问询后按科室方向推荐，不强制填齐所有病情字段。日期已知直接列余号，号别和上下午是可选筛选条件；号别和时间联合协商，不擅自改变患者意向。唯一候选得到明确接受时直接进入预约准备。

后台独立保存每轮完整对话、参考资料、判断依据、模型输出、状态及号源快照。工作人员前台通过可信后端读取记录。Dify本身仍只有一个患者回答通道，两套前台由同事分别实现。

咨询选定时段后输出私有booking_workflow_inputs，恰好对应预约工作流的两个输入：booking_payload和patient_token。后端在患者点击预约时补齐令牌后调用。选好时段尚未占号；hold占位180秒，confirm才是正式预约成功。

## 交付文件

- exports/consultation.yml、exports/booking.yml：可导入 DSL。本次迁移包按要求预填医院服务密钥；目标 Dify 应用密钥和模型密钥需另行配置。
- 医院导诊系统开发文档.docx：功能、业务设计与FDE复盘、架构、流程图、全部节点配置及测试用例。
- API对接说明.md、client_example.py、openapi.json：后端对接资料。
- knowledge：知识原文与来源；nodes：节点源码。
- service.py、compose.yaml、ssrf_proxy_medical.conf：医院服务与部署配置。
- tests、reports、test_*.py：单元测试、实际流程验证和结果。

## 迁移步骤

1. 用compose.yaml启动医院服务并保留数据库卷，配置与Dify容器连通的网络。
2. 导入knowledge中的知识资料，创建医院导诊知识库。
3. 导入两个exports下的DSL，重新绑定咨询流程的知识检索节点。
4. 设置API_BASE_URL和SERVICE_API_KEY，配置可用模型。本机模型为deepseek-flash。
5. 检查医生目录、余号接口和后台记录接口，运行测试，发布两个应用。
6. 将两套应用API密钥与医院服务密钥放入业务后端环境变量，接入真实登录身份与工作人员权限。

本机Dify使用Ubuntu-24.04内独立Docker Engine，启动注意事项见项目的Dify启动指引。医院接口本机地址http://127.0.0.1:8095，容器地址http://medical-guidance:8095。密钥不进入患者浏览器。本迁移包仅明文提供医院服务 API 密钥，详见《00 迁移部署指南.md》。

## 验证

本轮通过48项单元测试、6次公开接口调用链、6次科室及简短回复验证、11轮连续预约对话及3次直接交接办理、11轮业务可用性回归、3轮单一候选对话及5次完整交接办理、20人并发抢号。26次草稿运行、4项故障注入、真实180秒到期和重启持久化沿用同日未受本轮修改影响的既有证据。详情见reports/test_summary.json及各原始报告。

当前医院目录为14名医生，14天滚动号源，每个医生时段容量为一；连接实际医院系统时按医院接口规则调整。患者身份登录、工作人员角色鉴权、收费和通知由业务系统接入。

经验 skill 位于 skills/dify-business-workflows，可复制到本机 Codex skills 目录复用。包含角色与业务边界、基础问询、自然确认、前后台分离、事务交接、本机部署注意事项和小步迭代约定。它不自动桥接当前两个工作流；联动方式见开发文档第9章与API对接说明。
