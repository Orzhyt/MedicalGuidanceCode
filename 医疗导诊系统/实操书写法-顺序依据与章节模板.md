# 实操书写法：章节顺序的依据 + 任务页模板 + 样章

> 用途：解决两个写作卡点
> 1. 目录顺序凭什么这么排？是人的判断还是 AI 给的？
> 2. 「构建项目目录」这类步骤，学员到底操作什么？

---

## 一、顺序的依据：不是知识顺序，是「最小可运行路径」顺序

### 1.1 先承认一件事

现在这份目录的顺序，**看起来像 AI 生成的**，原因是：它同时符合两种排法，而你没有在书里写明选的是哪一种。

- **分层顺序**（AI 最常给）：前端 → 后端 → 数据库 → 部署。
  问题：学员做完前端页面，后端还没影，全程看不到东西跑起来，第 3 天就想放弃。
- **竖切顺序**（你现在这份）：每章切一刀，切完系统就能跑、能演示。
  好处：每章都有可见产出。代价：必须解释「为什么这一刀切在这」。

你的目录是竖切，这是对的。缺的只是把依据写出来。

### 1.2 四条排序规则（写在序章，全书复用）

| 规则 | 含义 | 在你目录里的体现 |
|---|---|---|
| 先能跑，再能看 | 没有可运行的进程，任何代码都无从验证 | 环境准备 → 服务初始化 |
| 先能存，再有身份 | 账号要先有地方落库，登录才有意义 | 数据持久化 → 登录系统 |
| 先读后写，先无状态后有状态 | 只读功能出错不影响数据；写操作有冲突、有脏数据 | 导诊（只读）→ 预约（写 + 时段冲突） |
| 先可 Mock，后真依赖 | 外部系统不可控，先用假实现打通自己的链路 | GuidanceService Mock → Day2 换 Dify；9090 可用性风险押到最后 |

### 1.3 每章必须署名「为什么是现在」

在这门课里，顺序的真正依据是**依赖 + 风险**，而这两件事只有作者知道。所以每章开头固定两句话：

> **为什么是现在**：本章之前，系统只能（上一章的终点）；本章之后，系统能（本章终点）。
> **本章不做什么**：（把诱惑挡在门外，防止学员提前跑偏）

例：

> 为什么是现在：上一章结束时，你有一个能打开的空白首页；这一章做完，用户注册的数据真正落进了数据库文件，关掉浏览器再打开还在。没有这一步，下一章的「登录」就只是一次性的内存状态。
> 本章不做什么：不设计用户表之外的任何表，不做权限分级。

这两句话一写，读者不会再怀疑顺序是抄来的。

### 1.4 你现有目录的四个结构问题

| 位置 | 问题 | 改法 |
|---|---|---|
| 「SuperPowers 完成项目技术选型」 | 工具名进了标题。工具会换代，标题不该绑定；而且技术选型**不该由 AI 决定**，学员要带着约束去问 | 标题改为「技术选型与约束固化」，正文里 SuperPowers 只是手段之一 |
| 「数据持久化」与「数据库对接」 | 「数据库对接」在登录章下，和上一章重复，学员会以为是两件事 | 合并：数据持久化章讲清「连接 + 建表 + 读写验证」，登录章只讲「用户表 + 加密 + 会话」 |
| 导诊/预约下的「1.接口 2.页面 3.联调」 | 这是按技术层切，不是按学员动作切。学员会读成三个独立任务 | 改成一次连续会话的三个检查点：先定契约 → 再出页面 → 再接真数据，每段都有验收 |
| 全书缺少 | 没有「AI 协作规范」（上下文怎么给、什么时候重开会话、怎么让 AI 只改一个文件）、没有每章的演示节点 | 加一章前置「与 AI 协作的四条纪律」；每章末尾固定「演示 60 秒」 |

## 二、任务页模板：实操书的最小单元

一本书由 30～40 个「任务页」组成，不是由 7 个「章」组成。学员是一页一页做的，所以颗粒度必须落在任务上。

### 2.1 一个任务页的八个字段

```
【标题】动词开头 + 可观察结果        例：让首页在 localhost:3000 打开
【时长】15–25 分钟（超过 30 分钟必须拆）
【这一页结束时你手上有什么】一句，必须是能看到/能点/能查的东西
【为什么现在做】依赖上一页的什么产出
【你要做的决策】2–3 个选项 + 默认推荐 + 判断依据（这是教学重点，不是步骤）
【给 AI 的输入】可直接复制的提示词 + 学员必须自己补的那部分上下文
【验收清单】3–5 条，能勾选、能执行、能被别人复核
【翻车与修复】症状 → 原因 → 一句话修复（写 3 条，来自你自己踩过的）
```

### 2.2 关键认知：学员操作的不是代码，是四类动作

这是回答你第二个问题的核心。AI Coding 课上，如果任务页写成「输入命令 → 复制代码」，这本书就退化成命令手册，学员离开 AI 什么都不会。学员真正要练的是：

| 动作 | 学员具体做什么 | 在书里怎么体现 |
|---|---|---|
| **决策** | 在 2–3 个方案里选一个，并说出理由 | 「你要做的决策」字段，给默认值但要求学员改一处 |
| **约束** | 把模糊需求变成 AI 能执行的边界（技术栈、目录、不许动什么） | 提示词里的「约束」段，故意留空一行让学员填 |
| **验收** | 不看代码，用现象判断对不对 | 验收清单 + 判断题（给 5 个场景问「放哪个文件」） |
| **修复** | 报错时先定位到哪一层，再让 AI 只改那一处 | 翻车表 + 「只贴报错，不贴整个文件」的纪律 |

一句话：**书要教的是「怎么指挥 AI 和怎么验收」，不是「这段代码写了什么」。**

## 三、样章：构建项目目录（可直接改进 docx）

> 归属：服务初始化 章 → 第 2 节
> 时长：20 分钟
> 这一节结束时你手上有什么：一个能 `npm run dev` 打开的项目，以及一份写进 `AGENTS.md` 的「文件归属规则」。

### 3.1 为什么现在做这件事

目录结构不是分类习惯，它声明两件事：**依赖往哪个方向流**、**哪个点可以被替换**。

这门课后面要做两件必然发生的事：Day2 把导诊从 Mock 换成 Dify、把挂号从假数据换成 9090 真接口。如果你的代码里「页面直接 fetch 外部系统」，这两次替换就要改十几个文件。所以目录必须在写第一行业务代码之前定下来，并且定成「可替换」的形状。

**这一节不做什么**：不建空目录占位，不为「以后可能用到」预留任何文件夹。

### 3.2 学员要做的决策（只有一个，但必须自己拍）

| 选项 | 长什么样 | 适合谁 |
|---|---|---|
| A. 按技术分层 | `frontend/` + `backend/` 两个独立项目 | 前后端分别部署、不同人维护 |
| B. 单体 Next.js 全栈（**默认推荐**） | 一个项目，`app/` 里既有页面也有 `api/` 路由 | 本课程：一个人、三天、要频繁联调 |

选 B 的理由要讲透：这门课的难点不是部署架构，是「让 AI 在正确的边界里改代码」。两个项目意味着每次改动都要跨目录对齐类型和接口，学员的注意力会从「业务流程」转移到「工程协调」。**先跑通，再拆。**

学员需要自己填一行：如果你选 A，写出你必须承担的额外成本（提示：类型共享、跨项目联调、两份部署配置）。

### 3.3 操作步骤

**第 1 步 · 生成脚手架（学员亲手敲，只有这一条命令）**

```bash
npx create-next-app@latest medical-guide --ts --tailwind --app --eslint --src-dir=false --import-alias "@/*"
cd medical-guide
git init && git add -A && git commit -m "chore: scaffold"
```

预期：`npm run dev` 后浏览器打开 `localhost:3000` 能看到默认页。
先提交一次，是为了让后面 AI 的每一次改动都能被 `git diff` 看见——这是本课程后面所有「验收」的基础。

**第 2 步 · 让 AI 重组目录（学员只审，不动手建文件夹）**

把下面这段发给 AI。注意最后三行「约束」是本节的考点：**学员要学会用约束换可控**。

```text
你是本项目的架构师。当前是一个刚用 create-next-app 生成的 Next.js 15 项目
（App Router + TypeScript + Tailwind），业务是「智能导诊 + 医生预约」。

不要写任何业务代码，只做三件事：
1. 输出目标目录树（tree 格式），在现有结构上增补，顶层需要包含：
   app/  components/  lib/  services/  types/  specs/
2. 每个目录后面用一句中文注释写明：职责 + 什么不许放进来
3. 给出一条依赖规则，用箭头表示谁能 import 谁

约束：
- 只为「本周真要写的代码」建目录，不预留空文件夹
- 不引入新依赖，不改 package.json
- 业务代码一律不许直接调用外部系统（Dify、挂号系统 9090），必须经过 services/
```

**第 3 步 · 学员手动修正一处（强制动作）**

AI 大概率会给你一棵「看起来很完整」的树，其中必然有 20% 是空壳。学员的任务是删掉至少两个目录，并写下删除理由。

参考结论（这是本节真正的知识点）：

```text
app/            路由与页面。不许放业务逻辑，不许直接 fetch 外部系统
app/api/        只做「收参数 → 调 services → 返回 JSON」，三行以内
components/     纯展示。不许 import services/，不许知道 Dify 和 9090 的存在
lib/            无 UI 的纯函数与基础设施（db 连接、日期、加密）。不许 import components/
services/       唯一允许访问外部系统的地方
  guidance/     导诊：mock.ts 与 dify.ts 两个实现，index.ts 决定用哪个
  registration/ 挂号系统 9090 的 HTTP 客户端
types/          跨层共享的契约（请求/响应结构）。被所有人 import，自己不 import 别人
specs/          给 AI 看的规格文档，不是运行时代码
```

依赖方向只有一条：**app → services → lib**，`components` 只能被 `app` 引用。箭头不许反向。

**第 4 步 · 把规则固化进 AGENTS.md（学员亲手写，5 行）**

这是「固化」的含义：规则不写在你的脑子里，写在 AI 每次都会读的文件里。

```markdown
## 目录与依赖规则
- 依赖方向：app → services → lib，禁止反向 import
- 任何外部系统调用只能出现在 services/ 下
- app/api/*/route.ts 只做参数校验 + 调 service + 返回，不写业务逻辑
- 新增目录必须在本文件登记，否则视为违规
```

### 3.4 验收清单（学员自查，不看代码看现象）

- [ ] `npm run dev` 能打开首页，控制台无红色报错
- [ ] 终端执行 `find . -maxdepth 2 -type d -not -path "./node_modules*" -not -path "./.git*"`，输出的目录每一个都能说出用途
- [ ] `AGENTS.md` 里有「目录与依赖规则」一节，且是学员自己打的字
- [ ] `git log` 至少有 2 次提交（scaffold / structure）
- [ ] 能用一句话回答：明天导诊从 Mock 换成 Dify，要改哪几个文件？（答案：只改 `services/guidance/`，`app/` 一行不动）

**五道判断题**（学员口述，同伴复核；答错说明目录没建对）

1. 新增「科室列表」接口 → `app/api/departments/route.ts`
2. 写一个调用 9090 查可预约时段的函数 → `services/registration/client.ts`
3. 把 `2026-11-04` 格式化成 `11月4日 周三` → `lib/date.ts`
4. 一个玻璃拟态按钮 → `components/ui/glass-button.tsx`
5. 在聊天页里请求导诊结果 → `app/chat/page.tsx` 里调 `/api/chat`，**不**直接 import 服务

### 3.5 常见翻车

| 症状 | 原因 | 修复 |
|---|---|---|
| 花了 40 分钟一个个手建文件夹 | 把「构建目录」当成打字任务 | 目录由 AI 生成，学员只审；手只用来删 |
| 树里出现 `hooks/ utils/ helpers/ config/` 四套并列 | AI 默认给「完整模板」 | 用约束顶回去：「只为本周代码建目录」 |
| `components/chat.tsx` 里出现 `fetch('http://localhost:9090')` | 没定依赖方向，AI 就近放置 | 移进 `services/`，在 `AGENTS.md` 补一条禁令 |
| 目录建完，第二天还是随手乱放 | 规则只存在于对话里 | 第 4 步的固化，比第 2 步重要 |

### 3.6 一句话记住

> 目录不是给文件分类，是给「依赖」和「未来要替换的东西」画边界。

## 四、全书节奏建议

- 每章 3–5 个任务页，每页 15–25 分钟，一章≈半天。
- 每章最后固定一页「演示 60 秒」：学员站起来，用 60 秒演示本章终点，讲不出就是没做完。
- 每章最后固定一页「如果 AI 不听话」：本章最可能出现的 3 个失控场景（它擅自加依赖 / 它改了你没让改的文件 / 它一次给你 800 行）。
- 前置加一章「与 AI 协作的四条纪律」（30 分钟，不写代码）：
  1. 一次只让它改一个文件；
  2. 需求先写进 `specs/`，再让它读，不在对话里口述；
  3. 它改完先 `git diff`，看不懂的改动一律回退；
  4. 报错只贴报错和出错文件，不贴整个仓库。

## 五、下一步

按上面的模板，`环境准备` 与 `服务初始化` 可以先落成 6～8 个任务页，跑一遍真实操作，把「翻车表」替换成你自己踩过的坑，再往下写。翻车表如果是编的，学员一试就穿帮；如果是真踩的，这本书就有了别处抄不到的价值。
